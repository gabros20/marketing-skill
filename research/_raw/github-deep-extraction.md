## 1. google/meridian

**SOURCE**: github.com/google/meridian (Apache-2.0, LICENSE at repo root, 1472★, pushed 2026-07-31). Note: the repo ships NO `docs/` folder — Meridian's documentation lives externally at developers.google.com/meridian and is generated separately from the code; the richest primary-source material is actually the Python docstrings in `meridian/model/*.py`.

**WHAT IT TEACHES**:
- **Adstock mechanics** (`meridian/model/adstock_hill.py:377-378`): Meridian implements adstock as `adstock_{g,t,m} = sum_{i=0}^max_lag media_{g,t-i,m} · alpha^i`, i.e. a weighted rolling sum over a lag window, computed per-geo/per-time/per-channel. Two decay families are supported: **geometric** (single parameter `alpha` in [0,1], fixed decay) and **binomial** (a reparameterized alternative, `adstock_hill.py:93-99, 194-205`). `alpha=0` is a valid "no adstock" point-mass prior.
- **Saturation via Hill function** (`adstock_hill.py:304-328`): `t1 = media^slope; t2 = ec^slope; return t1/(t1+t2)`, i.e. the classic two-parameter Hill/logistic saturation curve with an `ec` (half-saturation point) and `slope` parameter per channel. Hill and Adstock can be composed in either order (`adstock_hill.py:380-383`); order matters for whether batch/posterior dimensions propagate.
- **ROI/mROI/contribution as prior TYPES, not just outputs** (`meridian/model/spec.py:85-109`): Meridian lets you place the Bayesian prior directly on `roi_m`/`roi_rf` (ROI), `mroi_m`/`mroi_rf` (marginal ROI), `contribution_m`/`contribution_rf` (% of outcome), or `beta_m`/`beta_rf` (raw regression coefficient) — `media_prior_type` and `rf_prior_type` select which. Default is `'roi'`.
- **The calibration-with-experiments mechanism (the triangulation argument)** — `spec.py:114-137`: `roi_calibration_period` is a boolean array over `(n_media_times, n_media_channels)` marking which historical weeks an incrementality experiment covers. "The ROI numerator is the incremental outcome generated by media executed during the calibration period... The denominator is the channel spend during calibration period." In effect: you don't bolt the experiment result on afterward — you tell the model "for these specific weeks, we have ground-truth ROI from an experiment," and it uses that as the informative Bayesian prior constraining the ROI coefficient, while historical (uncalibrated) values are used for all other weeks. This is the literal Bayesian-prior-as-triangulation-device mechanism.
- **Hierarchical geo modeling** is a first-class mode (`knots.py`, `context.py`; confirmed externally, see below) — geo-level data is "encouraged if available" and lets the model borrow statistical power across markets; national-level is a fallback with fewer identifiable parameters.
- **Model-fit philosophy (from developers.google.com/meridian/docs/post-modeling/model-fit, fetched 2026-08-01)**: Meridian explicitly subordinates predictive fit to causal identification. Quoted (24 words): *"directly validating the quality of causal inference is difficult"* without a designed experiment — hence indirect diagnostics (out-of-sample R²/MAPE/wMAPE, sensibility checks on baseline and channel dominance, posterior credible intervals) are used instead. Critical stated caveat: a model can look well-fit in-sample while still being causally biased if a real confounder is dropped for the sake of a tighter fit; the docs favor deliberately keeping a plausibly-overfit but fully-confounder-complete model over a leaner but confounded one.
- **Data requirements (from developers.google.com/meridian/docs/pre-modeling/collect-data, fetched 2026-08-01)**: media inputs must be "summable" quantities (impressions, clicks, spend), never rates (CTR, CPC); minimum 2 years of weekly data for geo models, 3 years for national; weekly granularity is the stated best-practice equilibrium between noise and resolution (daily → longer runtime, monthly → non-convergence risk).
- **Explicit relationship to google/lightweight_mmm** (developers.google.com/meridian/docs/migrate, fetched 2026-08-01): Meridian is positioned as "the official evolution of the Google MMM approach" / successor to LightweightMMM, adding automatic experiment calibration (manual-only in LMMM), native reach-and-frequency modeling, an ROI-parameterized prior option, automatic Google-Query-Volume confounder handling, and hierarchical control variables — at the cost of slower MCMC (TensorFlow Probability vs. LMMM's Numpyro backend). The page does not say LMMM is deprecated, only superseded.

**VERBATIM-WORTH-KEEPING** (2 quotes max, license Apache-2.0 permits reuse with attribution but charter caps quotes anyway):
1. "directly validating the quality of causal inference is difficult" — developers.google.com/meridian/docs/post-modeling/model-fit (fetched 2026-08-01).
2. "The ROI numerator is the incremental outcome generated by media executed during the calibration period" — meridian/model/spec.py:116-117 (Apache-2.0).

**RELEVANCE TO PACK JOBS**: attribution-and-measurement (flagship material — this is the single richest primary source on GitHub for MMM mechanics and experiment-calibration methodology); paid-acquisition (ROI/mROI vocabulary, diminishing-returns/saturation concept practitioners need to know exists even outside formal MMM).

**CREDIBILITY NOTE**: Primary source — Google engineering repo + Google-hosted docs, top rung of the ladder. Code inspected directly (highest confidence); the five docs-page extracts came via WebFetch summarization (not direct HTML read), so treat exact wording beyond the two quoted fragments as paraphrase-fidelity, not verbatim-fidelity. Docs pages carry as-of dates (2026-07-09, 2026-05-15 — Google's own "last updated" stamps) confirming this is current guidance, not stale.

## 2. facebookexperimental/Robyn

**SOURCE**: github.com/facebookexperimental/Robyn (MIT, LICENSE at repo root, "Copyright (c) Meta Platforms", 1498★). `README.md`; `R/R/transformation.R`; `R/R/calibration.R`; `R/R/inputs.R`; `R/R/model.R`.

**WHAT IT TEACHES**:
- **Adstock, R implementation, two families** (`R/R/transformation.R:44-105`): `adstock_geometric(x, theta)` — single fixed decay rate; docstring gives explicit rule-of-thumb ranges by media genre: "TV c(0.3, 0.8), OOH/Print/Radio c(0.1, 0.4), digital c(0, 0.3)" (theta bounds). `adstock_weibull(shape, scale, type=CDF|PDF)` — two-parameter, flexible decay; **critically, Weibull PDF (not CDF) is the only variant that supports a *lagged* peak** (effect building before decaying, e.g. brand-awareness media whose impact peaks days after exposure) — CDF always peaks at time zero.
- **Saturation via Hill, same functional family as Meridian** (confirmed via `python/spec/src/robyn/modeling/pareto/hill_calculator.md` — an LLM-generated Python-port spec, lower fidelity than the R roxygen docs but structurally consistent): alpha (shape) and gamma→inflexion (half-saturation) parameters per channel, fit from adstocked media.
- **The `robyn_calibrate()` mechanism — direct-fit calibration** (`R/R/calibration.R:6-64`): a *separate, standalone* function (marked BETA/experimental, usable independently of the main MMM) that takes `df_curve` (spend + response pairs from a real experiment — "Recommended sources of truth are Halo R&F or Meta conversion lift") and fits Hill saturation-curve parameters (alpha/gamma) directly to that experimental curve via iterative optimization (`max_trials`, `max_iters`, convergence tolerances). Output gamma ranges (e.g., 2.5th–97.5th percentile) can then be fed back in as hyperparameter bounds for the main model.
- **The `calibration_input` mechanism — the classic/production calibration path** (`R/R/inputs.R:16-27, 113-121`; used throughout `R/R/model.R`): `robyn_run()` accepts a `calibration_input` data.frame with columns `channel, liftStartDate, liftEndDate, liftAbs, spend, confidence, metric` per experiment. Robyn's stated guidance: "We strongly recommend to use experimental and causal results that are considered ground truth to calibrate MMM. Usual experiment types are people-based (e.g. Facebook conversion lift) and geo-based (e.g. Facebook GeoLift)." Robyn only accepts **point-estimates**, not confidence ranges, as calibration input, and explicitly warns the point-estimate must match the *tested increment*, not the full channel spend (e.g., a 70%-holdout test on $100k spend implies a $30k point-estimate, not $70k). Mechanically, this calibration input becomes an additional term (`mape_lift`, `calibration.R:632`) folded into Robyn's multi-objective loss function (alongside NRMSE and decomp.RSSD), which Nevergrad's evolutionary optimizer then minimizes jointly — a materially different mechanism from Meridian's Bayesian-prior approach (see convergence section below).

**Maintenance status finding (as-of 2026-08-01, via `gh api`)**: repo metadata shows `pushed_at: 2026-01-26`, but the actual commit log's most recent substantive commit is **2025-06-27** (`5915aa9`, "fix: refresh window end issue"); the gap between the metadata push date and the last real commit suggests only tag/release housekeeping since mid-2025. 114 open issues; the 5 most recently filed (Jan–Jun 2026) all have **0 comments** — no maintainer engagement visible on new issues for well over a year. The README itself flags the Python port as "a LLM-translated Beta version and might encounter bugs," and independently notes it was built using Llama-based translation from the R original, with known translation-fidelity risk acknowledged by the maintainers. **Assessment: Robyn is functionally in low-maintenance/community-only mode as of this date — a fact worth flagging given Robyn is frequently cited as a MMM tool of comparable standing to Meridian.**

1. "We strongly recommend to use experimental and causal results that are considered ground truth to calibrate MMM" — R/R/inputs.R:18-19 (MIT).
2. "TV c(0.3, 0.8), OOH/Print/Radio c(0.1, 0.4), digital c(0, 0.3)" — R/R/transformation.R:49-50 (MIT), theta bounds by media genre.

## Meridian vs Robyn: where two independent MMM implementations agree

Built by different companies (Google vs. Meta), different teams, different math stacks (TensorFlow Probability/Bayesian MCMC vs. ridge regression + Nevergrad evolutionary search) — yet they converge on:

1. **The same two-stage transform shape**: adstock (carryover/decay) → saturation (diminishing returns), applied per media channel, in that conceptual order — Meridian's `adstock_hill.py` and Robyn's `transformation.R` implement structurally the same pipeline despite unrelated codebases.
2. **The same saturation functional form**: both use the **Hill function** (`t1/(t1+t2)` with a slope/shape and an inflection/half-saturation point) as a first-class saturation curve, not merely one option among many — Meridian: `adstock_hill.py:304-328`; Robyn: `hill_calculator.md` (alpha/gamma) and referenced throughout R model code.
3. **Both offer more than one adstock decay shape and flag that the simple fixed-rate ("geometric") version is a limiting case of a richer, more flexible family** — Meridian's binomial decay vs. Robyn's Weibull CDF/PDF are different specific generalizations, but both projects independently concluded a single fixed-decay-rate parameter is insufficient and shipped a second, more flexible decay family.
4. **Both treat incrementality experiments as the mechanism that anchors/disciplines the observational model, not as an optional afterthought** — Meridian's `roi_calibration_period` (a Bayesian-prior constraint over ROI/mROI) and Robyn's `calibration_input` (a loss-function term penalizing deviation from lift-test point-estimates) are mechanically different (prior vs. loss-penalty) but serve the identical purpose: forcing the model's channel-level ROI estimate to agree with ground-truth experimental results (Meta conversion lift / GeoLift for Robyn; unnamed "experiments and other prior information" for Meridian) rather than relying purely on the shape of the observational time series. **This is the single strongest piece of convergent evidence for the pack's attribution-and-measurement job: independent teams at rival companies both concluded that MMM without experiment calibration is insufficiently trustworthy, and both built explicit machinery to bolt experiments on.**
5. **Both explicitly warn calibration/experiment inputs must be point-estimates of the tested increment, not full-channel totals or confidence bands** — Robyn states this directly (`inputs.R:26-28`); Meridian's ROI-numerator-is-the-incremental-outcome-during-the-calibration-period framing (`spec.py:116-117`) encodes the same discipline implicitly.
6. Neither tool claims MMM alone (without experiment calibration) fully resolves causal identification — Meridian says so explicitly ("directly validating the quality of causal inference is difficult"); Robyn's entire `calibration_input`/`robyn_calibrate` machinery exists precisely because uncalibrated MMM decomposition is treated as insufficient ground truth.

## 3. AnswerDotAI/llms-txt

**SOURCE**: github.com/AnswerDotAI/llms-txt (Apache-2.0, LICENSE at repo root, 2541★). `nbs/index.qmd` (the spec itself, authored by Jeremy Howard, dated 2024-09-03), `nbs/ed.md`, `nbs/domains.md`, `CHANGELOG.md`.

**WHAT IT TEACHES — exact spec contents**:
- File location: `/llms.txt` at a website's root (or optionally a subpath).
- Required structure, in order: optional BOM → **required** H1 (project/site name) → blockquote short summary → zero-or-more free markdown sections → zero-or-more H2-delimited "file list" sections, each a markdown list of `[name](url): optional notes`.
- A reserved **"Optional"** H2 section has special semantics: its links may be skipped if a shorter context is needed — an explicit token-budget mechanism.
- Separately proposed (not part of the core `/llms.txt` spec, but bundled in the same proposal): serving a clean **markdown mirror of every page** at the same URL with `.md` appended (or `index.html.md` for extensionless URLs) — this is what the authors call `llms-full.txt`-adjacent tooling in their own nbdev projects (all nbdev-generated docs sites now auto-emit `.md` twins by default, per this repo).
- Companion tooling described: `llms_txt2ctx` (CLI that expands an `llms.txt` into `llms-ctx.txt` / `llms-ctx-full.txt`, i.e. concatenated/XML-wrapped context files) — again, this is downstream tooling around the spec, not the spec itself.

**Adoption / consumption claims — the load-bearing finding**: The authors do **not** claim any AI vendor's system automatically fetches or consumes `/llms.txt` at inference time. The spec text itself states the expectation is usage "on demand when a user explicitly requests information" (e.g., a developer manually loading docs into a coding-assistant context) — not automatic crawling. `nbs/ed.md` illustrates the intended workflow via an explicitly **hypothetical** enhanced text editor ("this hypothetical `L` (load) command," "In this LLM-enhanced version of `ed`") that a user must invoke to fetch and inject the file — i.e. even the authors' own illustrative example requires a human- or tool-initiated fetch, not passive crawler consumption. `nbs/domains.md` even ships a DIY Python test script instructing site owners to manually fetch their own `llms.txt`, parse it with `llms_txt2ctx`, and feed it to Claude to check whether *that specific chat session* can answer questions about the content — which only demonstrates that a human-orchestrated pipeline can use the file, not that any AI system natively discovers or fetches it unprompted. **No claim anywhere in the repo that ChatGPT, Claude, Perplexity, or any other assistant automatically checks `/llms.txt` when browsing/crawling a site.**

## 4. knadh/listmonk

**SOURCE**: github.com/knadh/listmonk (AGPL-3.0, LICENSE at repo root, 22563★, pushed 2026-07-30). `docs/docs/content/concepts.md`, `docs/docs/content/bounces.md`, `docs/docs/content/querying-and-segmentation.md`, plus `cmd/subscribers.go` and `internal/manager/manager.go` for header implementation.

**WHAT IT TEACHES — the real mechanics a self-hosted email system forces you to face**:
- **Bounce processing is not automatic-by-default** — must be explicitly enabled (Settings → Bounces) before POP3 scanning or bounce APIs activate (`docs/docs/content/bounces.md:1-3`).
- **Bounce classification is heuristic, not authoritative**: listmonk "applies a series of heuristics looking for keywords in the bounced mail body to guess if it is a 'soft' bounce or a 'hard' bounce" (SMTP status codes like 4.x.x/5.x.x, strings like "mailbox not found"); if no heuristic matches, it defaults to 'soft' (`bounces.md:18`) — i.e., bounce hard/soft classification in practice is a best-effort guess layered on inconsistent provider behavior, not a clean protocol signal.
- **Multi-channel bounce ingestion**: native webhook support for AWS SES, Azure Communication Services, SendGrid/Twilio, Postmark, Forward Email, Lettermint — each provider has its own event shape that listmonk normalizes (`bounces.md:45-55`).
- **RFC 8058 one-click unsubscribe is implemented, not merely documented**: `cmd/subscribers.go:894-895` and `internal/manager/manager.go:531-533` both set `List-Unsubscribe-Post: List-Unsubscribe=One-Click` alongside `List-Unsubscribe: <url>` — confirming the actual header pair the RFC requires is wired into outbound campaign sends, not just described in docs.
- **Subscriber model**: a subscriber is identified by email+name; can belong to zero ("orphan"), one, or many lists; **subscription status is per-list, not per-subscriber** — `unconfirmed` (added without consent, still receives single opt-in sends), `confirmed` (clicked the confirmation link — required before receiving double opt-in list sends), `unsubscribed` (`concepts.md:25-33`).
- **Double opt-in is a list-level property**, not account-level — a list is configured single- or double-opt-in independently; only double opt-in lists gate sending behind explicit confirmation-link click (`concepts.md:41`).
- **Attributes/segmentation is raw JSON + arbitrary Postgres SQL fragments**, not a fixed schema — segmentation queries run directly against `subscribers.attribs` (JSONB) using Postgres `->`/`->>` operators, including nested-path queries and joins against `campaign_views` to segment "opened this campaign" cohorts (`querying-and-segmentation.md:69-100`). This is a materially lower-level (and more powerful, but less guided) segmentation model than typical SaaS ESPs expose.
- **Campaign analytics primitives are pixel + click-tracking**, both explicitly flagged in the docs as carrying GDPR-relevant privacy implications, with an anonymized-tracking option offered specifically to decouple opens/clicks from subscriber identity (`concepts.md:61-67`).
- **Templates** are Go-template-based, support arbitrary logic, and include an `{{ OptinURL }}` field specifically for building double opt-in confirmation emails (`templating.md:59`, confirmed via grep).

**VERBATIM-WORTH-KEEPING**:
1. "applies a series of heuristics looking for keywords in the bounced mail body to guess if it is a 'soft' bounce or a 'hard' bounce" — docs/docs/content/bounces.md:18 (AGPL-3.0; re-expressed above, this is the one direct quote used).

## 5. dubinc/dub

**SOURCE**: github.com/dubinc/dub, LICENSE.md at repo root. **License finding (must be read to characterize, per charter)**: dual-structure — the bulk of the repo is **AGPLv3** ("Content outside of the above mentioned directories or restrictions above is available under the 'AGPLv3' license"), but two specific directory trees are carved out under a **separate proprietary/commercial license** defined in `apps/web/app/(ee)/LICENSE.md`: `apps/web/app/(ee)` and `apps/web/app/app.dub.co/(dashboard)/[slug]/(ee)`. - **What counts as a "click"** (`apps/web/lib/zod/schemas/clicks.ts:5-36`, `packages/tinybird/datasources/dub_click_events.datasource`): a click event is keyed by `click_id` + `link_id` + `timestamp`, enriched with parsed geo (continent/country/region/city/lat-long), device/browser/OS/engine (parsed from user-agent), a `bot` flag (UInt8 — bot-detected traffic is captured, not silently dropped, letting downstream consumers filter it out), a `qr` flag distinguishing QR-code scans from ordinary link clicks, and a `referer`/`referer_url` pair. Crucially, **click "trigger" is a first-class classified field with four distinct values**: `TRIGGER_TYPES = ["qr", "link", "pageview", "deeplink"]` (`apps/web/lib/analytics/constants.ts:183`) — i.e., Dub's data model treats a QR scan, a direct link click, a passive pageview-based tracked event, and a mobile deeplink open as **four separate kinds of "click,"** not variants of one thing.
- **Conversion attribution mechanism**: click, lead, and sale events form a joined chain via the shared `click_id` (`packages/tinybird/datasources/dub_lead_events.datasource`, `dub_sale_events.datasource` both carry `click_id` and `link_id` alongside their own `event_id`/`event_name`/`customer_id`). - **UTM handling**: Dub supports **named, reusable UTM templates** (`utm_source, utm_medium, utm_campaign, utm_term, utm_content`, plus a non-standard `ref` parameter) that can be attached to links in bulk (`apps/web/app/api/utm/[id]/route.ts`), rather than requiring UTMs to be hand-built per link.
- **Deep links** are handled as a distinct app route/module (`apps/web/app/app.dub.co/(deeplink)`) with dedicated middleware caching (`cache-deeplink-click-data.ts`) — deeplinks are architecturally separated from ordinary redirects, consistent with the four-way `trigger` taxonomy above.

## 6. plausible/analytics

**SOURCE**: github.com/plausible/analytics (AGPL-3.0, LICENSE.md at repo root, 28236★, pushed 2026-07-31). Chosen over Matomo per the brief's "pick whichever has richer marketing-facing docs" — Plausible's `lib/plausible/ingestion/acquisition.ex` is an unusually explicit, fully-commented channel-classification algorithm, which is the single richest "hidden gem" file across all six repos walked.

**WHAT IT TEACHES — referrer/channel classification, the actual taxonomy logic**:
- `lib/plausible/ingestion/acquisition.ex` implements `get_channel/5`, which classifies every visit into exactly one of **17 acquisition channels** using a fixed if-else precedence cascade (first match wins): Cross-network → Paid Shopping → Paid Search → Paid Social → Paid Video → Display → Paid Other → Organic Shopping → Organic Social → Organic Video → **AI Assistants** → Organic Search → Email → Affiliates → Audio → SMS → Mobile Push Notifications → Referral → Direct (fallback).
- **The base taxonomy is explicitly GA4's**, sourced from a bundled `priv/ga4-source-categories.csv` derived from Google's own published GA4 source-category reference (per the module's own doc-comment, citing support.google.com/analytics/answer/9756891). Plausible states its own deltas from GA4 explicitly in the module docstring: (1) a hand-maintained `@custom_source_categories` list adds sources GA4 doesn't cover, most notably **grouping ChatGPT, Claude, Perplexity, Grok, Gemini, Copilot, Phind, and DeepSeek into their own dedicated "AI Assistants" channel** — a taxonomy addition GA4 itself does not make, and a direct signal of where the industry's channel taxonomy is heading as AI-assistant referral traffic grows; (2) Google/Bing paid-search detection is inferred from `gclid`/`msclkid` URL parameters specifically because "Google is in a privileged position to analyze paid traffic from within their own network" — i.e., third-party analytics tools cannot reliably detect Google/Bing paid clicks from UTM alone and must special-case the platform's own click-id parameters; (3) a maintained list of known-paid `utm_source` values (e.g. `yt-ads`, `facebook_ad`, `adwords`) is auto-classified as paid regardless of what `utm_medium` says, because practitioners frequently mislabel or omit `utm_medium` on paid campaigns.
- **Precedence-order logic reveals real disambiguation rules practitioners rarely see written down**: e.g., `paid_medium?/1` is a **regex**, not an exact match list — `~r/^(.*cp.*|ppc|retargeting|paid.*)$/` — meaning any utm_medium containing "cp" (cpc, cpm, cpa), or literally "ppc"/"retargeting", or starting with "paid", is treated as a paid signal; `referral?/2` falls back to "any non-empty source not already claimed by a more specific rule" — i.e., **"Referral" is a residual/catch-all bucket for known-but-unclassified sources**, only below Direct as the true fallback for *no* source at all.
- **Goal model** (`lib/plausible/goal.ex`): three distinct goal types share one schema — custom `event_name` goals, `page_path` (URL-visit) goals, and a **scroll-depth goal type** (`scroll_threshold` field) as a first-class goal kind, not a bolt-on. Revenue/currency fields and multi-step funnels are gated behind an `on_ee` (enterprise-edition) code path within the *same* AGPL-3.0 codebase — i.e., Plausible's open-core split is feature-flagged at the code level, not directory/license-separated like Dub's.
- **Cookieless/GDPR posture** (README.md, direct read): explicit claim of "No personal data or IP addresses are stored, and no cookies or persistent identifiers are used," positioned as compliant with GDPR/CCPA/PECR; managed-cloud data processing is contractually restricted to EU-owned infrastructure specifically to satisfy Schrems II.
